Turn past SQL repairs into reusable experience

Experience-based SQL correction learns from historical mistakes: it contrasts an incorrect SQL with its ground-truth answer, attempts a repair, and distills reusable experience to guide future tasks.

What the shipped TK-Store rules look like

118 rules in the shipped store: 52 generic, 66 db-scoped. Text below is verbatim from tkstore/tkstore_sqlite.csv.

In test, most of the rules retrieved are generic. Only a small protion of rules are DB-scoped (which can be problematic as later discussed.)

Generic
  • Rule 1Output numeric type/precision matches evaluation expectations (integer-like vs decimal)
  • Rule 2Calendar-aware date parts (year/month/day extraction) are preferred over average-day approximations when exact component semantics matter
  • Rule 3If category assignment depends on a related table, enforce membership with EXISTS (or equivalent) before aggregation
  • Rule 4directionality of entity-pairs is explicitly respected in queries when measuring routes, flows, or connections
DB-scoped
  • E_commerce · order_payments.payment_valueWhen computing AOV from integer-like aggregates, verify whether SQLite integer division is expected before forcing float math
  • Baseball · player.debut, player.final_gameFor year-span components in SQLite date arithmetic, prefer STRFTIME-based component extraction over julianday/365 approximations
  • California_Traffic_Collision · parties.party_safety_equipment_1When segmenting collisions by helmet usage, first restrict to cases with motorcycle-related safety-equipment evidence using EXISTS against parties
  • Brazilian_E_Commerce · olist_order_payments.order_idIn order-level payment analyses joined to item-level tables, deduplicate order-payment pairs before counting category-level totals

What MAGIC's generated guideline looks like

One global checklist mined from failed training repairs, then given to the corrector on test SQL.

  1. 1Always aggregate at the correct entity level and handle ties when comparing segment-level minimums; compute all requested differences, not just one
  2. 2Select the right attribute from the correct table and join by the right key
  3. 3When computing a customer-specific rate, first identify the CustomerID from the triggering event
  4. 4Return event type from the event table when asked for event category at a location; avoid unnecessary joins that can drop rows
  5. 5Use the correct definition and quoting for T-BIL; list patient IDs per sex with GROUP_CONCAT and filter by the proper threshold

Observations & Conclusions

  2. 2Gains from generic knowledge diminishes with the use of stronger LLMs / better agents.
  3. 3We need to extract knowledge that are orthongonal to generic knowledge, domain specific knowledge (e.g., knowledge related to underlying data asset) seems more promising to be mined.
